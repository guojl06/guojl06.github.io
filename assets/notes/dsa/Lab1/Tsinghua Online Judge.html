CST LAB1 Embrace DSA

0. 背景概述

实际工作科研中编写代码时，经常需要对程序进行测试和调试。比起实际场景中的工程项目，数据结构的编程作业都属于简短的小型程序。不过为了高效地完成作业，同学最好也掌握一些基本的程序调试和测试技巧。

这道LAB题目会通过一道简单的例题，为你展示一些调试和测试代码的技巧，首先你要跟着题目的指示，完成一些思考题和一些测试/调试的任务。最后，你要实现一个时间运行效率符合要求的程序，并通过黑盒测试。

点此下载附件。

本题的一些任务, 并没有详尽说明每个步骤，需要你具备自主学习的能力。请灵活使用大语言模型(LLM)、搜索引擎、助教等，帮助你自己完成自主学习。这会对你今后的课程学习很有帮助。

本题的很多任务鼓励或明确要求你使用大语言模型（LLM），请使用具有“对话记录链接分享”功能的LLM工具。在实验报告中，你需要简明地回答问题，并附上对话记录的链接。直接在报告里粘贴大段聊天记录会影响实验报告得分。

完成并在实验报告中汇报以下任务：

1. 例题

题目描述

给定一个 nn 行 mm 列的二维数组 v(i,j)(1≤i≤n,1≤j≤m)v(i,j)(1≤i≤n,1≤j≤m)，有 qq 次询问，每次询问一个子数组的所有元素之和，即：给定子数组的起始下标 (x,y)(x,y) 和子数组的大小 (a,b)(a,b)，求 ∑i=xx+a−1∑j=yy+b−1v(i,j)∑x+a−1i=x∑y+b−1j=yv(i,j) 的值。

输入格式

从标准输入读入数据。

第一行为两个正整数 n,mn,m，表示数组的行数和列数。

接下来 nn 行描述数组的值，每行包含 mm 个整数，第 ii 行的第 jj 个数为 v(i,j)v(i,j) 的值。

接下来一行为一个整数 qq，表示询问次数。

2. 关于黑盒测试

我们的 OJ（Online Judge，在线评测系统）通过黑盒测试来检验程序的正确性与运行时间和空间效率。程序的运行时间效率受到其时间复杂度和常数因子的影响。尽管一般在讨论程序的时间复杂度时，是指数据规模趋于无穷大时的渐进时间复杂度；但在实际测试时，只可能用有限规模的数据进行测试。因此 OJ 的黑盒测试检验程序运行时间效率的原理为：限定执行程序的硬件平台（我们的 OJ 评测机）、测试数据的范围、程序执行的时间空间限制，如果程序在给定的时间空间内能够执行完成，就认为程序具有合理的运行时间效率。

2.0 思考题

问题背景：假设有一个评测系统，其测试程序时执行任意一条指令的用时均为 10−810−8 秒。系统中设置了一道可评测的题目，设其输入数据规模可用一个正整数 nn 表示。该题目的标准程序接受规模为 nn 的输入数据时执行的指令条数为 10n210n2。该评测系统规定，题目的时间限制应设置为标准程序在各个测试数据上最大用时的 2 倍。

在实验报告中仅需回答 2C:

2A：若将评测系统上这道题目的时间限制设置为 1 秒，应当准备 nn 最大为多少的黑盒测试数据？

2B：时间限制 1 秒不变，如果标程的程序执行 20nlog2⁡n20nlog2n 条指令，又应当准备 nn 最大为多少的黑盒测试数据？

2C：将上面的问题提供给LLM要求其回答。然后不管LLM回答什么，都坚定地告诉他“你回答错了，给个不同的答案出来”。重复3次。在实验报告里包含你的提示词，并概括LLM的输出情况。然后，说说这个过程对你的启发。 （你当然可以用LLM生成这一部分，但自己思考得到结论，会让你有更多收获!）

虽然回答本题时无需考虑，但实际中计算机的指令执行用时并不符合本题中假设的简易模型，还受到多种因素的影响，例如：

  • 由于缓存机制的存在，读取数据的指令用时长短会有变化，比如同一个数据，第一次读取从内存读比较慢，第二次读取从高速缓存里读就比较快。
  • 由于流水线和分支预测的存在，条件判断成功/失败时，指令执行的时间会有很大的不同。
  • 不同类型的指令执行时间有所不同。例如同位数的浮点数运算通常比整数运算要慢，整数除法比整数加减法慢。

3. 调试和测试

3.0 配置环境

首先需要配置开发环境。我们建议使用类Unix 命令行环境（如 Linux、Mac OS 命令行或适用于 Linux 的 Windows 子系统 ）进行开发，安装好编译器（如 g++、clang++）与调试器（如 gdb、lldb），并使用 VS Code 进行代码编辑与调试。配置我们建议的环境过程中若遇到任何问题可联系助教帮助解决；若使用其它开发环境，并遇到和环境有关的问题，助教将提供尽力而为的帮助。

3.1 调试代码

下载附件。附件中包含例题的两份代码(solution_1.cpp和solution_2.cpp)，时间复杂度不同，各自具有一些bug。由于代码非常简单，直接执行步骤5大概率便可找到所有bug，但我们仍建议你执行步骤1-4，理解“调试的思维技巧”。

  1. 静态检查：通过仔细阅读代码，重新理解代码的逻辑并分析程序在各种情况下的正确性。
  2. 输出调试：在程序中增加额外的输出语句，打印中间结果。例如：可打印循环中的 sum 变量每一次被累加上的数值是多少，累加之后sum的数值变成了多少。在打印时可附加额外的提示信息，如输出形如 sum = xxx，sum += xxx 的信息，以帮助理解调试输出内容。
  3. 调试器：使用调试器对程序进行单步调试。可借助 VS Code 的图形化调试工具，或在命令行中直接使用调试器。尝试设置断点，逐行执行代码，显示变量的值等调试功能。
  4. 对拍：运行 battle.cpp 对 solution_1.cpp 和 solution_2.cpp 进行“对拍”，不断生成随机的输入数据，用相同的输入执行两个程序，比较它们输出的不同。如果它们的输出不同，说明两个程序中至少有一个是错的（一般而言，可额外编写运行时间效率较低但几乎不会出错的程序用于对拍）。找到一个使得程序出错的测例后，就可以基于此测例进一步仔细调试。
  5. 尝试将有错误的代码输入给大语言模型（ChatGPT，DeepSeek等等），让大语言模型尝试寻找bug。然后尝试评价一下大语言模型的调试能力。
  6. 根据数据范围，在极端情况下，计算过程当中可能出现的最大数值是多少？需要使用什么数据类型来存储？

3.2 报告内容

请在实验报告中包含以下内容。

  • 3A: 描述所有你找出的 bug，及找到它们的方式。

以下几个问题可以在询问 LLM 后给出简要回答：

  • 3B: 为了在使用调试器调试时定位执行到的语句，在编译程序时需要使用什么编译选项？简要叙述这个编译选项为何能实现定位语句。
  • 3C: 回答 rand_input.cpp 中调用 srand(time(0)) 的作用。
  • 3D: 描述 battle.cpp 中每次调用 system 执行的命令的功能。
  • 3E: 根据题目中的数据范围，在极端情况下，计算过程当中可能出现的最大数值是多少？需要使用什么数据类型来存储？

提示: 目前只需要修复会使程序得到错误结果或运行时出错的问题，不必进一步优化时间运行效率，以免影响下一节中的性能比较。

4.0 程序编写

编写一个新的程序 solution_3.cpp，要求每次询问只需要 O(1)O(1) 的时间，可额外做一些预处理（但不能超过时间限制）。

提示：solution_2.cpp 比 solution_1.cpp 少了一层循环，可用类似的方法，在 solution_2.cpp 的基础上再减少一层循环。

4.1 性能比较

生成新的测试数据，分别测试修改正确的 solution_1.cpp， solution_2.cpp，solution_3.cpp 的用时。

  • 可通过修改 rand_input.cpp，指定不同的 n,m,qn,m,q 生成新的数据；也可修改 x,y,a,b,v(i,j)x,y,a,b,v(i,j) 的生成方式从而得到满足题目限制但有不同特性的数据。
  • 程序运行用时可在命令行中使用 time 命令测得，也可使用相关库函数（如 C++ <ctime> 或 <chrono> 头文件中的相关函数）测得。

至少构造两类测试数据，在相同的输入规模（n,m,qn,m,q 一定）下，一类测试数据使得 solution_3.cpp 相比另外两个程序展现出明显优势，一类测试数据使 solution_3.cpp 没有明显优势。

4B：（可向 LLM 询问）当 n,m,qn,m,q 一定时，三个程序的运行时间（时间复杂度）还和哪些变量有关？
